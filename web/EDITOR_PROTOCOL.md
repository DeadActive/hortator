# Hortator editor protocol 1 (SysEx over USB MIDI)

Hortator is DEADACTIVE's drum-machine fork of Felucca for the FM-1 (fork: 2026 DEADACTIVE). This document specifies
how the web editor (`webapp/editor`, sources `web/editor/`) talks to a Hortator FM-1 running firmware 0.28.0 or
later. The protocol's shape — framing, 14-bit values, 7-bit groups, one request at a time, WATCH keep-alive and
pushes, the backup LIST / GET shape and the result codes — follows **upstream Felucca's editor protocol**
(hugelton/Felucca 5d9694d, `web/EDITOR_PROTOCOL.md`, `firmware/src/editor.c`; GPL-3.0-only, © Leo Kuroshita /
Hügelton Instruments). Hortator protocol 1 is not compatible with upstream's: its own header, command table and data
model (8 drum tracks, variations, lock banks). Design: `docs/superpowers/specs/2026-10-31-web-editor-design.md`.

## 1. Framing

```
request  F0 7D 48 54 <cmd> <seq> <args…> F7
reply    F0 7D 48 54 <cmd> <seq> <rc> <fields…> F7          rc 0: the command's fields
         F0 7D 48 54 <cmd> <seq> <rc> <detail> <msg…> 00 F7  rc ≠ 0: an error reply (any command)
push     F0 7D 48 54 <cmd> 7F <fields…> F7                   cmd 0x40..0x4F, only while WATCH is on
```

- `7D` is the non-commercial SysEx id, `48 54` is "HT". Upstream Felucca uses `7D 46 4C`; the update path uses
  `F0 00 32 xx …` (ota.c's frames: pack7 of `00 59 cmd …` as a bit stream, so the wire starts `00 32` and a byte whose
  low two bits are `01`; the installer's handshake is `F0 00 32 45 00 00 00 40 7F F7`) and the keys
  `F0 22 24 35 7D|7F F7`. They never share the first data bytes.
- Every data byte is 7 bit. A request is at most **640 bytes between F0 and F7** (usb_app.c `sx_frame`; longer ones
  are dropped by the USB driver, unanswered). A reply or push is at most **400 bytes, F0 and F7 included** (the
  editor's reply buffer): lists in replies are cut to fit and say where they stopped (`first`, the list's count,
  `total` / `nnames`): ask again from there.
- `seq` (0..126) is chosen by the page and comes back in the reply. Pushes carry `7F` and answer nothing. Frames
  shorter than `F0 7D 48 54 cmd seq F7` are dropped unanswered.
- **Every request gets exactly one reply** with its cmd and seq — unknown commands too (rc 1 detail 43), and commands
  of a capability this firmware lacks (rc 1 detail 46) — except while the editor is silent (§4 rule 4).

### Field types

| Type | Bytes | Encoding |
| --- | --- | --- |
| u7 | 1 | 0..127. In slot / track fields `7F` = "the current one" or none (stated per field) |
| u14 | 2 | `lo, hi`: value = lo \| hi << 7, 0..16383. `3FFF` = none (preset id, page column) |
| v14 | 2 | a u14 holding value + 8192: −8192..8191 (as upstream) |
| u35 | 5 | 7 bits each, least significant first: a u32 (CRC-32, magic, storage sequence) |
| str | n + 1 | ASCII 32..126, then `00`. The device's degree sign (LFO PHASE's unit) is sent as `deg` |
| list | 1 + … | a u7 count, then that many items |
| pack | rest | pack7 of the data bytes: groups of up to 7 bytes, each preceded by one byte holding their top bits (bit j = bit 7 of byte j); upstream's `ed_unpack7` format. 256 bytes pack to 293. It runs to the end of the frame |
| state | 17 | the state block (§3) |
| step | 3 | `flags, cond, note` (§2.4) |
| nudge | 1 | a step's NUDGE + 64: −50..+50 as 14..114 (minor 1, §2.4) |

### 2.1 INFO and versions

- INFO's request and its first four reply fields (magic, firmware, major, minor) never change in any protocol
  version. `firmware` is the version as `VERSION.txt` holds it, without the `DRUM-` prefix.
- **caps** (u14): 0x01 LIVE (PAGES DESC GET SET TEXT DUMP SELECT WATCH; pushes CHANGED STATE), 0x02 PRESETS (NAMES
  PRESET_LOAD), 0x04 PATTERNS (STEPS_GET STEPS_SET LOCKS_GET LOCK_EDIT CUE SAVE; pushes STEPS_CHANGED LOCKS_CHANGED),
  0x08 BACKUP (BACKUP_LIST BACKUP_GET), 0x10 RESTORE, 0x20 NUDGE (minor 1: STEPS_GET's reply ends with each step's
  NUDGE, STEPS_SET may carry it; §2.4), 0x40 UPR2 (minor 2: the user presets are "UPR2", 96 slots each holding the
  voice and its FX; backup object 0 is that record, nuser 96; §2.3, §6), 0x80 SAMPLES (minor 3: SMP_INFO ..
  SMP_RENAME, the user sample slots; §2.7). 0.28.0 has all eight (0xFF); earlier 0.28
  builds answered minor 0, caps 0x1F, then minor 1, caps 0x3F (user presets "UPR1": 128 voices), then minor 2, caps
  0x7F. The page hides what a missing bit covers (no NUDGE: it never sends the field and shows no NUDGE; no UPR2: it
  reads that FM-1's presets as the new firmware will move them, but never writes them, and says to update the FM-1
  first; no SAMPLES: the Samples tab says to update the FM-1).
- **minor** grows with additions an older page can ignore (commands, push types, flag bits, fields appended at a
  reply's end, optional fields at a request's end). A **major** change breaks the page: it refuses another major (§7).
  Minor 1 (NUDGE): an older page reads STEPS_GET's 64 steps and stops there; its STEPS_SET without the field leaves
  each written step's NUDGE as the device has it (§2.4), so it never clears one by accident. Minor 2 (UPR2): an older
  page's preset restore (1,284 B, "UPR1") is refused (rc 2 detail 24, nothing written); it cannot read the new record.
  Minor 3 (SAMPLES): new commands only; an older page never sends them, an older device answers them rc 1 detail 43.
- INFO also clears the device's memory of the last (cmd, seq) (§4 rule 3): every connection starts with INFO.

### 2.2 Knobs: PAGES, DESC, GET, SET, TEXT, DUMP, SELECT

- **scope** 0 = a track's parameter (`P_*`, id 0..pcount − 1; `track` 0..7, 7F = the selected one); 1 = a global
  (`G_*`, id 0..gcount − 1; `track` ignored, send 0); 2 = a model's SOUND knob (DESC only: `track` = the model
  0..nmodels − 1, `id` = its knob 0..7, independent of any track). Ids are the firmware's `core.h` enums (P_MODEL 0,
  P_E0..P_E7 1..8, P_LEVEL 9 … P_IMIX 75; G_BPM 0 … G_DMODE 41); `web/editor/device_data.json` names them.
- **Values** are the knob's set value (what the knob shows), never the LFO / MOTION / lock modulation of the moment:
  GET, SET's reply, DUMP and CHANGED all report MOTION's base and, on a locked step, the value under the LOCK.
- **PAGES** lists, in the device's order, the pages of its page table the editor may show, resolved for the
  selected track **now**: the pages of scope track or global except the PROJECT / COPY (slots), MOTION and SONG pages
  and the pages holding a knob past G_COUNT (TOOLS, GLOBAL 3/7: MUTE, METRO, THRU, QUANT — device settings, not
  project data). The GLO pages DLY (two), REVERB (TYPE ROOM / SPRNG / HALL, SIZE, DAMP) and CHORUS (RATE, DEPTH) are
  global pages like GLOBAL and SYSTEM (graphs 17..19: the device's drawings of the echoes, the tail, the sweep). A column is a parameter id or `3FFF` (empty). SOUND
  columns are the selected track's SOUND list (MODEL, P_E0..P_E3, the P_E4..P_E7 whose label does not start with
  `-`, LEVEL, PAN, NOTE, CHOKE, PRIO), a SOUND page past the list's end left out; GRIDS shows G_GLEN1..3 where it has
  G_GX / G_GY / G_GCHAOS while G_GMODE is EUCLID; the LFO DEST page becomes four pages "DEST 1".."DEST 4" (columns:
  that slot's SRC, DEST, DEPTH, then `3FFF`). `scope` 0 track / 1 global; `graph` is the device's `GR_*` (a drawing
  hint; graph 10 = LFO: columns 1–2 are LFO 1's, 3–4 LFO 2's, as the device draws the page in two halves). Re-read
  PAGES after a selection change, after the selected track's MODEL changed and after G_GMODE changed.
- **DESC**: fmt (`core.h` F_*: 0 INT, 1 PCT, 2 BIPCT, 3 TIME, 4 LFOHZ, 5 CUTOFF, 6 DB, 7 SEMI, 8 ENUM, 9 BPM, 10 NOTE,
  11 ONOFF, 12 OCT, 13 STEPS, 14 CTHR, 15 CRAT, 16 CATK, 17 CREL, 18 CMKUP, 19 LRATE1, 20 LRATE2, 21 LDEST,
  22 LPHASE, 23 NOTEO, 24 RDECAY, 25 FDEC, 26 SRR), min / max / def, the label and unit the device shows, and the
  value names from index `first` (as many as fit; `nnames` = how many there are: ask again from first + count):
  - ENUM: the names of the values min..max (the name of v = names[v − min]).
  - INT with names (flag SPLIT): the range split evenly over the n names: v's = names[⌊(v − min) · n / (max − min + 1)⌋].
  - LDEST (an LFO DEST): the 19 values' names as the device shows them for that track now (OFF, the knob a DEST moves
    by its label or `--`, R.TUN … F.RES).
  - flags: 0x01 SPLIT; 0x02 ORDER (the device shows the values in another order: DESC with `first` = 7F gives it, a
    list of value − min by place; MODEL's order is the MODEL knob's list); 0x04 LOCK (lockable: LOCK_EDIT accepts
    it); 0x08 RO (shown, not settable: SET answers rc 1 detail 45); 0x10 CONTEXT (depends on the track's MODEL,
    INSERT TYPE or RESON MODEL: re-read it after those changed).
  - Read-only globals: G_MIDI, G_INFO, G_SLOT, G_NAME, G_LOAD, G_SAVE, G_CLRSEQ, G_INITSND.
- **GET** returns up to `count` consecutive values from `id` (stopping at pcount / gcount and where the reply is
  full: about 25), each with the device's own text (≤ 5 characters: "1/16.", "1.4k") and unit. The page shows the
  text as it comes and never formats values itself.
- **SET** acts as the device's knob: clamped to the range; a read-only knob: rc 1 detail 45 "READ ONLY" (checked
  before RESTORING). MODEL loads the model with its **first factory preset**, as the MODEL knob does (DUMP then shows
  that preset id, not edited; a model without one: its default sound, no preset); ACID onto a third track: rc 2
  detail 18. RESON MODEL past its caps: rc 2 detail 0 with the device's message ("RESON: 4 TRACKS MAX", "CHORD: 2
  TRACKS MAX", "MODAL: 2 TRACKS MAX"). A knob the track's preset holds marks it edited when it changes, as on the
  device: a SOUND knob always; one of the FX a user preset holds (§6: the sends, RESON, FILTER, INSERT, SRR) when the
  track was loaded from a user preset that holds its FX (not a factory or voice-only one; the SLICER, LEVEL, PAN, the
  LFOs never). MOTION's base (and a
  locked step's value under the LOCK) moves when MOTION plays that knob. Two knobs answer rc 0 **unchanged**, as their
  knobs on the device do: G_BPM while following an external clock (G_CLOCK not INT: the clock's tempo), and the
  PATTERN knobs (P_SLEN P_SDIV P_SSWING P_SRC) while a song plays (its rows set them). The reply is always the value
  kept and its text: show it. No CHANGED push echoes the editor's SET.
- **TEXT** formats a value of a knob for the track's current context without setting it (lock values, menus).
- **DUMP**: the track's model, its preset id (`3FFF` none; ids as PRESET_LOAD's), edited (0 / 1), all pcount
  values, then all gcount globals. No texts: GET them.
- **SELECT** selects a track as the track keys do: there is one selection (the device's). A STATE push follows.

### 2.3 Presets: NAMES, PRESET_LOAD

- Preset ids: 0..150 the factory presets in bank order (bank 0 MACHINEDRUM 0..54, 1 MODERN 55..94, 2 CLASSIC
  95..150), then 151..246 the user slots 0..95 (minor 1 and before: 151..278, slots 0..127). **NAMES** lists a
  factory bank, from `first`, as many as fit (bank 3 = the user bank: rc 1; user presets are read as backup object 0,
  their names live only in the page and files).
- **PRESET_LOAD** loads a preset onto a track as the device's PRESETS list does: MODEL and the 8 SOUND knobs; a user
  preset that holds its FX (used 1, §6) sets them too (RESON MODEL within its caps: a third CHORD / MODAL becomes
  STRNG, RESON on a fifth track OFF); a factory or voice-only preset leaves the track's FX. Never LEVEL, PAN, NOTE,
  CHOKE, the SLICER, LAYER, the LFOs or the steps. rc 2 detail 17: an empty user slot; detail 18: ACID onto a third
  track. The push shadows are not updated (editor_pattern.c): on the **selected** track the knobs that moved arrive
  as CHANGED pushes (as if turned on the device; at most 4 a pass); another track: no push. Neither carries the
  preset id (DUMP): the page re-reads the track it shows.

### 2.4 Patterns: STEPS_GET, STEPS_SET, LOCKS_GET, LOCK_EDIT, CUE, SAVE

- **step** (3 bytes): `flags` bit 0 ON, 1 ACC, 2 SLIDE, 3 TIE, bits 4..5 RATCH (hits − 1); `cond` the PROB code
  (0 = 100 %, 1..20 = 0..95 %, 21 1-SHOT, 22..56 A/B (1/2, 2/2, 1/3 … 8/8), 57 FILL, 58 !FILL; `device_data.json`
  `conds` gives the knob's order and names); `note` = the step's NOTE − C4 + 60 (60 = C4: a drum's transpose, ACID's
  note).
- **nudge** (NUDGE, minor 1, caps 0x20; `step_t.micro`): the step's hit moved by micro / 100 of the step, −50 (halfway
  to the previous step) .. +50 (halfway to the next), sent as micro + 64; the device shows it as `+25`, `-10`, `0`
  (STEP, a step held, KNOB 4). It is part of the step everywhere (projects, variations, copies) but travels after the
  steps, so the 3-byte step stays as protocol 1.0 had it: STEPS_GET's reply ends with 64 nudge bytes; STEPS_SET takes
  either `5 + 3 × count` bytes (no NUDGE: each written step keeps the device's NUDGE, except a step written empty —
  flags, cond 0, note 60 — which gets 0, as a tap turning a step off leaves it) or `5 + 4 × count` (the steps, then
  count nudge bytes, clamped to ±50). A firmware without NUDGE (minor 0) answers the longer form rc 1 detail 44.
- **STEPS_GET** reads what the device would play: `live` 1 = the loaded slot's playing variation (the live steps,
  unsaved edits included); other variations of the loaded slot and other slots come from the slot's RAM image (equal
  to flash unless the slot is marked unsaved). `used` 0 = a variation never used (steps all zero, timing 0 0 0 0);
  variation 0 (shown as 1) is always used. `timing` = LEN 1..64, DIV 0..9, SWG 0..100, SRC 0..3 of that track in that
  variation. An empty slot: rc 2 detail 16. No slot loaded (the power-on kit): slot 7F, its playing variation only,
  reads the live steps (reply slot 7F); other variations rc 2 detail 22.
- **STEPS_SET** writes steps of the **playing variation of the loaded slot** (slot 7F or the loaded slot; values
  clamped). Another variation of the loaded slot: the device **presses that variation's key itself** (owner decision
  3, switch-to-edit; the cue key's rules and refusals): stopped, the switch happens at once and the edit applies
  (rc 0; the reply has no state block: the switch arrives as a STATE push, with the timing knobs as CHANGED and a
  STEPS_CHANGED for the tracks that differ, never one for the steps written); playing, the switch is queued to the pattern's end (or already is) and the edit is refused with rc 5 detail
  32 "CUE FIRST": the page sends the same STEPS_SET again once a STATE push shows that variation playing — it must
  **not** send CUE for it (a second press of a queued key means "at the next step"). Also rc 5 detail 32: a slot is
  queued (wait for its switch), or `slot` is another slot (CUE it first). A song plays: rc 2 detail 2 "STOP TO
  EDIT". No slot loaded and another variation: rc 2 detail 22. A refused key: rc 2 with the cue's code (detail 1,
  8 + c). Edits are live (the slot's dirty bit) until SAVE. LEN / DIV / SWG / SRC are knobs (P_SLEN P_SDIV P_SSWING
  P_SRC): SET them.
- **Locks** belong to the slot and apply in every variation. **LOCKS_GET** lists a track's lock-bank events in the
  bank's order (step, then knob, MOTION before LOCK) from `first`, as many as fit: `kind` 1 = a MOTION event (held
  until the knob's next event), 2 = a parameter LOCK (that step only); `value` the knob's raw value (−64..127).
  **LOCK_EDIT** edits the live bank (the loaded slot's; with no slot loaded the power-on kit's): op 0 SET a LOCK
  (step, param, value clamped to the knob's range on that track; rc 2 detail 19 not lockable, 20 the bank is full:
  1024 events), op 1 CLEAR the LOCK at (step, param), op 2 CLEAR the step's LOCKs, op 3 CLEAR the track's LOCKs.
  MOTION events are never touched. Unused request fields: 0.
- **CUE** is exactly the device's cue keys (as of 0.26.0: SAVE + white keys 1–4 = slots A–D, the black keys =
  variations): kind 0 = `cue_slot(n)` (n 0..3), kind 1 = `cue_var(n)` (n 0..7). Playing: queued to the pattern's
  end; the same key again: at the next step; the playing slot's / variation's key: the queue is cancelled. Stopped:
  the switch happens at once. A slot cue plays that slot's last-played variation; a variation never used starts as
  a copy of the playing one. The reply's state shows the queue (qslot / qvar) or, stopped, the switch done; later
  switches arrive as STATE pushes. Refusals are rc 2 with the device's code and message: detail 1 VARIATIONS FULL,
  2 STOP SONG TO CUE, 3 SAVE TO A SLOT FIRST, 4 SLOT c EMPTY, 8 + c SAVE c FIRST (c 0..3: the slot whose unsaved
  variations hold the park).
- **SAVE** is the device's SAVE of the loaded slot (variations, lock bank, then the record; ~0.2 s, allow 2 s):
  stopped only (rc 3 detail 42 "STOP TO SAVE"); rc 2 detail 22 nothing loaded, 28 no flash this boot (state flag
  NOFLASH), 21 VARIATIONS FULL, 29 the USR2 / USR3 guard blocks writes this boot; rc 4 "SAVE ERROR". A slot other
  than 7F / the loaded one: rc 1 detail 45.

### 2.5 Backup: BACKUP_LIST, BACKUP_GET

Objects, read from flash — never RAM: a backup is what the device loads after a power cycle. Without flash this boot
(state flag NOFLASH) BACKUP_LIST, BACKUP_GET and RESTORE answer rc 2 detail 28 "NO FLASH".

| obj | Object | Size | Format (little endian; §6) |
| --- | --- | --- | --- |
| 0 | user presets | 3,204 | "UPR2" (minor 1 and before: 1,284, "UPR1") |
| 1–4 | project record A–D | 3,840 ("FDRG"; an "FDRF" one, saved before NUDGE, the same size); an older record its own size (§6) | `project_t` |
| 5–8 | lock bank A–D | 3,208 | "LKB1" `lk_bank_t` |
| 9–12 | variations A–D | 8 + used: 22..3,584 | "VAR1" `var_bank_t` |

- **BACKUP_LIST** gives all 13: present (0: no record in that slot, a lock bank / variations not linked (the record's
  lk_n / var_len 0), no user bank saved), size, crc (zlib CRC-32 of the bytes: the storage header's), seq (the
  storage sequence of the copy read), flags 0x01 UNSAVED (the slot or the user bank has changes in RAM that flash
  lacks: the page says "A has unsaved changes — SAVE on the FM-1 to include them"), 0x02 LOST (the record links an
  object no flash copy holds), 0x04 OLD (a record in an older format, FDRF included; the device converts it at load). A lock bank
  and variations are the copies the record links (either A/B copy), as the device loads them.
- **BACKUP_GET** reads 256 bytes (the last piece: what is left) at `offset` (a multiple of 256, below size) of an
  object whose seq came from BACKUP_LIST. rc 5 detail 33: it changed since (another seq: a SAVE in between): LIST
  again and read that object again from 0. rc 2 detail 30: not present. Check the CRC-32 of each complete object.
- A full backup, worst case: 3,204 + 4 × (3,840 + 3,208 + 3,584) = 45,732 B = 181 pieces, about 2–4 s.

### 2.6 RESTORE

One restore at a time: **BEGIN → DATA … → COMMIT** (or ABORT). The transport must be stopped.

| op | Request (after op) | Reply (after op) |
| --- | --- | --- |
| 0 BEGIN | kind u7 (0 user presets, 1 project), slot u7 (target 0..3; presets: 0), magic u35 (part 0's first 4 bytes, LE), 3 × {size u14, crc u35} (parts 0 record / presets, 1 lock bank, 2 variations; size 0 = none) | kind u7, slot u7 |
| 1 DATA | part u7, offset u14, data pack (256 bytes; the last piece what is left) | part u7, offset u14, len u14 |
| 2 COMMIT | — | kind u7, slot u7, state |
| 3 ABORT | — | — |

- **BEGIN**: playing: rc 3 detail 42, nothing changes. Presets: part 0 = 3,204 with magic "UPR2", parts 1 / 2 size 0
  (a "UPR1" record: rc 2 detail 24; the page moves an older bank into 96 slots itself, §5).
  Project: part 0 = 3,840 with magic "FDRG" or "FDRF" (a file made before NUDGE: it has parts 1 / 2 too), or an
  older record's magic with its size (§6; then parts 1 / 2 size 0); part 1 = 0 or 3,208; part 2 = 0 or 22..3,584. A
  record magic "FDR?" newer than "FDRG": rc 2 detail 23 "UPDATE THE FM-1 FIRST" (so an FDRG file sent to a device
  that predates NUDGE is refused by its magic, nothing staged); anything else wrong: rc 2 detail 24. A project with a variations part while the park buffer holds
  another slot c's unsaved variations: rc 2 detail 8 + c "SAVE c FIRST" (as the cue keys). A BEGIN while a restore
  runs drops that one first.
- From BEGIN to its end the device is **RESTORING** (state flag 0x01): it shows "RESTORING", refuses its own PLAY
  (start), cue keys, LOAD, SAVE, PASTE, NAME, preset save / delete, the TOOLS screen's pastes, DUPLICATE and CLEAR and
  a held step's KNOB 1–4 (PROB RATCH ACC NUDGE) (showing "RESTORING"; the TOOLS copies still work), records nothing
  live (QUANT's recording), and answers every editor
  write (SET, PRESET_LOAD, STEPS_SET, LOCK_EDIT, CUE, SAVE) with rc 6 detail 40; reads go on. A queued cue is
  cancelled. Data goes straight into the RAM homes the device has (record → `proj_slot[s]`, lock bank →
  `lk_slot[s]`, variations → the park buffer `var_buf[var_play ^ 1]`, presets → `upr`): the target's unsaved RAM
  changes are gone from BEGIN on (the page said so when asking).
- **DATA**: a part's pieces in order from offset 0, 256 bytes each (the last one shorter). A repeat of the last piece
  (a retry) is accepted again; another offset: rc 5 detail 34 (resend from the piece after the last one acknowledged).
  A wrong length: rc 1 detail 44. DATA / COMMIT / ABORT with no restore running: rc 1 detail 41.
- **COMMIT** (allow 2 s): every part complete (else rc 2 detail 27); each part's CRC-32 as BEGIN said (else rc 2
  detail 25, the restore dropped); the objects pass the device's boot checks (else rc 2 detail 26, dropped): presets
  "UPR2", used 0 / 1 / 3, model < nmodels, each move 0..96 (knobs clamped to the model's ranges, FX to theirs);
  a project `proj_ok` (FDRG, size, sum) or
  a known older magic + size + sum (FDRF as FDRG for its links), `lk_valid` with lk_n = its count and lk_link = its link, `var_valid` with
  var_len = its length and var_link = its link. Then the device **re-seals** the project for the target slot (the
  lock bank's and the variations' slot byte, the record's lk_link / var_link and sum), so a project file restores
  into any slot, and writes in the save order — variations, lock bank, then the record (the commit: with the A/B
  copies a power cut leaves the old or the new project whole) — in one uninterruptible step (~0.2 s; the update
  check right before it: the upgrade command pending → rc 6 detail 0 "UPDATE", the restore dropped, nothing
  written). Playing by then: rc 3, nothing written. Flash error: rc 4. Then the slot is reloaded from
  flash; the loaded slot is loaded again as LOAD does (its live edits replaced). Presets: one object written, the user
  bank reloaded.
- **ABORT**, an idle restore (3 s without any editor request), update traffic (§4 rule 4): nothing is written, the
  RAM homes are reloaded from flash (`proj_fetch`, `preset_user_boot`), RESTORING ends.
- An older-format record (FDR1..FDRE carry their motion inside) restores as part 0 alone, written as it is and
  converted at load as the device always does. An FDRF record restores with its lock bank and variations, re-sealed
  for the target slot with its magic kept, and is converted at load as flash's FDRF records are (KEYF, SRR and the
  INSERT out of steps 0..6's spare bytes, every NUDGE 0; BACKUP_LIST flags it OLD until the slot is saved again).
- Staging bound: every record format is at most `sizeof(project_t)` (3,840; `editor_backup.c` asserts it), a lock
  bank is `lk_bank_t`, variations at most `var_bank_t` (3,584): BEGIN accepts no other size and DATA writes below it.
- "Copy to…" another slot = BACKUP_GET the source's three objects + RESTORE them into the target.

### 2.7 Samples: SMP_INFO, SMP_BEGIN, SMP_DATA, SMP_END, SMP_READ, SMP_CLEAR, SMP_RENAME

The three user sample slots USR1..USR3 (the SAMPLE model's and the LAYER's sets after the built-in ones), in flash,
in upstream Felucca's slot format (Appendix): a 480-byte header at the slot's start, IMA ADPCM data at +512.

| slot | Name | Flash | Size | Data at most (`max`) |
| --- | --- | --- | --- | --- |
| 0 | USR1 | 0xA0000..0xB3FFF | 80 KiB | 81,408 B |
| 1 | USR2 | 0xB4000..0xBFFFF | 48 KiB | 48,640 B (the variations follow at 0xC0000) |
| 2 | USR3 | 0xC8000..0xD3FFF | 48 KiB | 48,640 B (the lock banks follow at 0xD4000) |

**The slot limits are law**: the device never erases or writes a byte outside the slot a command names, whatever
the request says (lengths, offsets, header fields), and never touches the Bluetooth store, the settings, the
projects, the presets, the variations or the lock banks.

- **SMP_INFO**: valid 1 = the slot holds a sample the device plays (its header passes the device's checks; then
  name (the header's 8 characters, trailing 0s dropped), len (data bytes), crc (the header's CRC-32 of the data), nz
  (zones), n (zone 1's samples) and rate (zone 1's rate, Hz / 44,100 × 65,536) are the header's); valid 0: empty
  (name "", len / crc / nz / n / rate 0). max = the data bytes the slot holds (the table). Slot > 2: rc 1 detail 45.
- **Upload: SMP_BEGIN → SMP_DATA … → SMP_END.** One at a time; the transport stopped throughout (the flash writes
  stall the audio).
  - **BEGIN** (allow 2 s): len = the data bytes (1..max; more: rc 2 detail 31 "TOO BIG", nothing changes), crc =
    the zlib CRC-32 of the data. Playing: rc 3 detail 42 "STOP TO UPLOAD". A restore running: rc 6 detail 40. The
    update command pending: rc 6 detail 0 "UPDATE". No flash this boot: rc 2 detail 28. USR2 / USR3 when its 48 KiB
    clamp failed this boot (the guard of §2.4's SAVE): rc 2 detail 29. Then the device stops the voices playing the
    slot and **erases the slot's first sector (its header)**: from here the slot reads empty, until END. An upload
    running is dropped first (its slot stays empty). The device shows "UPLOAD USR1".
  - **DATA** (allow 2 s): the data in order, 256 bytes a piece (the last one what is left) at offset 0, 256, 512 …
    (offsets in the data: the bytes go to the slot's +512 + offset). The first piece into a flash sector erases that
    sector. A repeat of the last piece (a retry) is answered again when flash holds it; another offset: rc 5 detail
    34 "OUT OF ORDER" (send from the piece after the last one acknowledged); a wrong length: rc 1 detail 44; no
    upload running for that slot: rc 1 detail 41 "NO UPLOAD"; playing: rc 3 detail 42 (the upload stays: STOP and
    send the piece again). **The update loader's sweep** (Appendix): a piece holding a sector's bytes +0xF00..+0xF4F
    that could read as an update record is refused, rc 2 detail 35 "DATA REFUSED", and the upload dropped (the slot
    stays empty). The page checks this before sending and avoids it (§5 samples).
  - **END** (allow 2 s): the header (480 bytes, the Appendix's layout). The device checks: every byte received (else
    rc 2 detail 27, the upload stays); the header: magic "FSMP", version 1, 1..16 zones, data length = BEGIN's len,
    CRC = BEGIN's crc, every zone inside the data and well formed (eng_sample.c `smp_user_scan`'s checks) (else rc 2
    detail 26, dropped); the CRC-32 of the data as flash holds it = crc (else rc 2 detail 25, dropped); the update
    command pending: rc 6 detail 0, dropped. Then it writes the header — bytes 4..479 first, the magic last — and
    reads the slot again: valid 1. A power cut at any point of an upload leaves the slot empty, never a sample made of
    two uploads or of an unwritten header.
  - An upload with no editor request for 3 s, and update traffic (§4 rule 4), drop it: the slot stays empty.
- **READ**: the slot's raw bytes, 256 a piece at offset (a multiple of 256) below 512 + len: the header sector's
  first 512 bytes (the header, then 32 bytes as flash holds them), then the data — what a backup file holds (§5).
  crc = SMP_INFO's: another one (the slot changed since) rc 5 detail 33 "CHANGED: READ AGAIN"; an empty slot rc 2
  detail 30 "NO DATA".
- **CLEAR** (allow 2 s): stopped only (rc 3 detail 42 "STOP FIRST"); the voices playing the slot stop and its
  header sector is erased: the slot is empty (its other sectors keep their bytes until the next upload reaches them).
  An upload running into that slot is dropped (the page's Cancel sends CLEAR).
- **RENAME** (allow 2 s): name = 1..8 characters, ASCII 32..126 (else rc 1 detail 45). Stopped only. An empty slot:
  rc 2 detail 30. The device rewrites the header sector (header and the first 3,584 data bytes, read first; the
  magic last): a power cut in its ~0.1 s can leave the slot empty, never garbage.
- SMP_BEGIN, SMP_DATA, SMP_END, SMP_CLEAR and SMP_RENAME are writes (§4 rule 3: a retry with the same seq gets the
  first reply again).
- A sample the editor makes is **one zone over all keys** (lo 0, hi 127, root 60, not looped): SMP_INFO's n / rate
  give its length (n / (44,100 × rate / 65,536) seconds). A restored backup keeps the zones it has (up to 16).

## 3. The state block (17 bytes)

| # | Field | Meaning |
| --- | --- | --- |
| 0 | playing | 0 / 1 |
| 1 | slot | the loaded slot 0..3; 7F none (the power-on kit) |
| 2 | var | the playing variation 0..7 (shown 1..8) |
| 3 | qslot | the queued slot 0..3; 7F none |
| 4 | qvar | the queued variation 0..7; 7F none |
| 5 | sel | the selected track 0..7 |
| 6 | flags | 0x01 RESTORING, 0x02 SONG running (cues refused), 0x04 NOFLASH (backup / restore / SAVE refused) |
| 7 | used | bit s: slot s holds a project |
| 8 | dirty | bit s: slot s has unsaved changes (the device's "A*", its breathing slot key) |

## 4. Rules

1. **One request in flight.** The page sends the next request only after the reply (or after giving up). The device
   holds one received SysEx frame; `ed_service()` takes `7D 48 54` frames and frees them in the same main-loop pass,
   answered or not, so the editor never holds the frame slot longer than one pass.
2. **Timeouts and retries.** 300 ms, 3 tries of the same frame (same seq); SAVE, RESTORE COMMIT and the sample
   writes (SMP_BEGIN, SMP_DATA, SMP_END, SMP_CLEAR, SMP_RENAME) 2 s. Each new
   request takes the next seq (0..126, wrapping); a retry keeps its seq.
3. **Duplicates.** The device remembers the last (cmd, seq) it handled. A write (SET, SELECT, PRESET_LOAD, STEPS_SET,
   LOCK_EDIT, CUE, SAVE, RESTORE, SMP_BEGIN, SMP_DATA, SMP_END, SMP_CLEAR, SMP_RENAME) arriving again with the same cmd and seq is not executed again: the answer is its
   first reply again, byte for byte (an rc 0 reply carries the data as it was then, its state block included). Reads
   are answered anew. The memory holds the last request only (any request replaces it); it is cleared by INFO and
   after 3 s without requests.
4. **Update silence (10 s).** Update traffic — an update frame (its first three bytes after F0 are `00 32 xx` with
   `xx & 3 = 1`: exactly the frames ota.c's `ota_take()` can decode to `00 59`, whatever the command), or the upgrade
   command `F0 22 24 35 7F F7` (`usb.ota_req`) — makes the editor silent for 10 s after the last such frame: no
   replies, no pushes, WATCH off, an uncommitted restore dropped (as ABORT). Editor frames arriving meanwhile are freed
   unanswered. Other SysEx (a DAW's `F0 7E` identity request, another maker's frames, upstream Felucca's `7D 46 4C`)
   is not update traffic: left for `ota_take()`, which frees it; the editor goes on. During `ota_session()` the editor
   never runs and `ota_take()` discards its frames; the device then holds one SysEx frame, and a page frame packed in
   the same USB packet as an updater frame can cost the update a retry. So the page, seeing timeouts, shows "FM-1 busy
   (update?)", sends nothing for the device's 10 s, then one INFO (one try) at a time with waits doubling from 10 s to
   60 s, and none after 2 minutes busy until the user clicks **Reconnect**; once INFO answers it reads everything again
   (INFO's state, PAGES, DUMP, the steps on screen).
5. **WATCH.** `WATCH 1` starts the pushes; they end 3 s after the last request of any kind (the page sends `WATCH 1`
   about every second when idle), on update traffic and on `WATCH 0`. At most 4 pushes per main-loop pass, only into
   a half-empty SysEx out ring, so a push never delays a reply. Pushes report device-side changes, never the
   editor's own writes; STATE is the exception (any change). After a STATE with another selection, slot or variation
   the page re-reads what it shows (DUMP, STEPS_GET, LOCKS_GET). Pushes (seq 7F) can arrive between a request and its
   reply: match replies by seq.
6. **Stopped-only flash writes.** SAVE, RESTORE BEGIN / COMMIT and the sample writes need the transport stopped (rc 3). User presets
   reach flash only through RESTORE of object 0 (the page edits the list; "Save track N here" reads the track with
   DUMP and puts its MODEL + SOUND knobs in the list).
7. **Nothing else goes out.** The page builds every frame with `proto.mjs encodeRequest`, which knows only this
   header and these commands: it cannot send `F0 00` (update), `F0 22 24 35 …` (keys) or another manufacturer's
   header (a web test checks it). Nothing is sent before the user clicks Connect; only INFO to a "Hortator" port;
   nothing else until INFO answered.
8. **MIDI clock.** Editor frames do not pause MIDI clock / THRU out; only update traffic does (3 s, as before). A
   306-byte frame holds clock out for ~7 ms (SysEx is never split): before a big transfer (Presets Read / Write,
   Projects Back up / Back up all / Restore / Restore all / Copy, Patterns Copy) while the FM-1 plays with SYNC
   (`G_SYNC`) not OFF, the page asks "Clock out may jitter during the transfer — stop first?" with Stop / Continue /
   Cancel. Protocol 1 has no transport command: Stop tells the player to press STOP on the FM-1 and the transfer
   starts when a STATE push shows it stopped.
9. **One page per browser.** Two pages on one FM-1 would each believe they own it (the restore lock is per page, the
   duplicate rule is keyed by (cmd, seq) alone). The page holds a Web Lock (`navigator.locks`, "hortator-editor"),
   with a BroadcastChannel fallback; a second tab shows "The editor is open in another tab" and "Use here", which
   makes the first tab disconnect and let go.

## 5. Files

JSON, UTF-8, one envelope:

```json
{ "format": "hortator-presets" | "hortator-project" | "hortator-backup", "version": 2,
  "firmware": "0.28.0", "protocol": 1, "created": "2026-10-31T12:00:00.000Z", … }
```

Readers ignore unknown keys; another `format` is refused ("Not a hortator-project file."); a higher `version` is
refused ("This file was made by a newer editor."). Version 2 (minor 2): user presets are 96 slots with their FX
(below); version 1 files (128 slots, the voice only) are still read. `summary` is informational: readers recompute it from the objects.
File names: `hortator-presets-<date>.json`, `hortator-project-<A..D>-<date>.json`, `hortator-backup-<date>.json`
(`<date>` = YYYY-MM-DD).

**hortator-presets** — readable, so rename / reorder / delete is list editing:

```json
{ …envelope, "slots": [ null | { "name": "K808 01", "model": 0, "modelName": "K808", "knobs": [0, 80, 40, 40, 30, 0, 0, 0],
                                 "fx": [0, 0, 20, 0, 0, 48, 72, 64, 100, 0, 64, 0, 1, 90, 0, 0, 40, 0, 64, 96, 96, 127, 0],
                                 "voiceOnly": true }, … 96 ],
  "moved": [0, 3, …32],
  "upr2": { "size": 3204, "crc32": "1a2b3c4d" } }
```

- The position is the device's user slot 0..95. `model` (the id) is authoritative, `modelName` informational,
  `knobs` = P_E0..P_E7 as int8, `fx` = the 23 FX the preset holds as int8, in §6's order (DIST CHO DLY REV, RESON
  MODEL TUNE DECAY MIX TONE STRCT POS KEYF, FILTER TYPE CUT RESO ENV DECAY, INSERT TYPE A B C MIX, SRR).
  `voiceOnly: true` (absent: false): the preset is the voice only (used 3: loading it leaves the track's FX; its `fx`
  are kept but not used). A slot without `fx` reads as the voice only. `name` (≤ 24 characters) lives only in the page
  and the files (owner decision 2: the FM-1 keeps showing its "MODEL NN"); a backup from the device names slots as the
  device does ("K808 01": `proto.mjs userPresetName`).
- `moved` (32 × 0..96, absent: all 0): where the device's older slots 97..128 went when it moved them in (slot + 1,
  0 none); the record keeps it so projects that name an old slot find its preset (§6). The page keeps it as read.
- "Write to FM-1" builds the UPR2 record (§6) from the list and restores it as object 0 (kind 0) with its CRC-32.
- `upr2` (top level, written by the page): `size` and `crc32` (as below: 8 lowercase hex digits) of the UPR2 record
  the file's `slots` and `moved` build — the bytes "Write to FM-1" would send. A reader that finds it builds the
  record and refuses the file when either differs ("damaged"); a file without it (hand-made) is read as it is. Names
  do not enter the record, so renaming in a text editor keeps the file valid; changing a model, a knob or an FX there
  makes it damaged. The presets of a hortator-backup carry no `upr2`.
- **Version 1** (before minor 2): 128 slots `{ name, model, modelName, knobs }`, checksum `upr1` (the 1,284-byte
  "UPR1" record). The page reads it as the firmware moves an older bank at its first start: slots 1..96 stay, the
  used ones of 97..128 go into the lowest empty slots (`moved` records where), each the voice only, its FX the
  power-on values; what finds no empty slot is left out and the page says how many. A slot's automatic name follows
  it to its new slot; a name given stays. The same for a version 1 backup's presets; its projects are as they are
  (their references to slots 97..128 follow `moved` when the device loads them).
- An FM-1 before minor 2 (no UPR2 cap) is read the same way (its "UPR1" record moved in for the list) but never
  written: the page says to update it first.

**hortator-project** — the device's objects byte for byte, plus a readable summary:

```json
{ …envelope, "slot": "A",
  "summary": { "name": "TECHNO 1", "models": ["BDTRX", …], "variations": [1, 2, 3, 5], "locks": 11, "format": "FDRG", "unsaved": false },
  "objects": { "record":     { "size": 3840, "crc32": "1a2b3c4d", "data": "<base64>" },
               "locks":      { "size": 3208, "crc32": "…", "data": "…" } | null,
               "variations": { "size": 310,  "crc32": "…", "data": "…" } | null } }
```

- `crc32` = 8 lowercase hex digits of the zlib CRC-32 of the decoded bytes; a reader checks each object's size and
  CRC and refuses a damaged file. `slot` is where it came from; it restores into any slot (§2.6). `unsaved` true:
  the file holds flash's version, not the device's unsaved edits.
- Projects reference user presets by slot number only, so restoring presets together with projects keeps names
  matching.
- Files kept `version` 1 across NUDGE (the record inside says its format); version 2 changed only the presets. A file made before NUDGE (its record
  "FDRF") restores into a device with NUDGE (converted at load, every NUDGE 0) and its variations can be copied (the
  page reads FDRF as the device converts it). A file made now (record "FDRG") sent to an FM-1 without NUDGE is refused
  by that device at RESTORE BEGIN (rc 2 detail 23 "UPDATE THE FM-1 FIRST"), nothing written.

**hortator-backup** — "Back up all":

```json
{ …envelope, "presets": { "slots": [ … as hortator-presets … ], "moved": [ … ] },
  "projects": { "A": { "slot": "A", "summary": …, "objects": … } | null, "B": …, "C": …, "D": … } }
```

**Sample backups** (minor 3) are not JSON: the raw slot, byte for byte as SMP_READ gives it — the 512-byte header
block, then the data (512 + len bytes) — named `hortator-sample-<USR1..3>-<name>-<date>.fsmp`. The page restores
one into any slot after checking it: magic "FSMP", version 1, 1..16 zones, file size = 512 + the header's data
length, the CRC-32 of the data = the header's, the data length ≤ that slot's `max` (else "Too big for USR2 (48 KiB)"),
every zone inside the data; it sends the header's bytes 0..479 as SMP_END's header, unchanged. Before sending any
sample the page checks the loader windows (Appendix) and refuses a file that has one ("This file cannot be written
safely"; a file the device made never has one).

**Samples the page makes** (Samples tab): one zone, off 0, n = the samples, loop 0 / n − 1, not looped, rate =
round(Hz × 65536 / 44100), root 60 (× 16 = 960), predictor / index 0, lo 0, hi 127; name ≤ 8 characters (ASCII
32..126, the file's name by default, upper case). The source (WAV, AIFF — whatever the browser decodes) is mixed to
mono, trimmed, optionally normalized (peak to full scale), and kept at its own rate when it is 44.1 kHz or less (else
44.1 kHz); when the result does not fit the slot (2 samples a byte: n ≤ 2 × max) the page offers lower rates
(halving down to 11,025 Hz, or the highest rate that fits) and shows the length and the rate. The ADPCM encoder
(`web/editor/sample.mjs`) runs the device's decoder in step (each nibble chosen so the device's decode follows the
source), so the page's preview — decoded from the encoded bytes with the device's decoder — is what the FM-1 plays.

## 6. Object layouts

Little endian; the firmware's structs (`presets.c`, `project.c`, `lockbank.c`, `varpack.c`), checked against the

- **User presets "UPR2"** (3,204): u32 magic "UPR2" (0x32525055), then 96 slots × 33 bytes: used u8 (0 empty: 33

## 7. Connecting, and the devices the page refuses

1. Nothing happens before the user clicks Connect (the browser asks for MIDI with SysEx).
2. **A port's name does not identify the device; INFO's answer does.** The name only chooses whom to ask first: macOS
   (CoreMIDI) keeps the name it first saw for a device, so a Hortator FM-1 that once ran Felucca or the stock firmware
   shows up as "Felucca" or "FM-1" although its USB product string is "Hortator". Ports named like an FM-1
   ("Hortator", "Felucca", "FM-1"; not Bluetooth ports): send INFO, one port at a time.
3. Never asked: a port in update mode ("Felucca Update" — the loader): "The FM-1 is in update mode". Other gear: nothing
   is sent unless the user clicks **Search other MIDI ports**, which sends INFO (only) to every other port too. With
   no port to ask: "No Hortator FM-1 found", the installer link and that search button.
4. INFO unanswered after its tries: **upstream Felucca** (its editor takes only `7D 46 4C` frames and drops this one),
   **the stock firmware**, **a Hortator before 0.28.0** (no editor), or a device busy updating — "This FM-1 does not
   answer the editor … Install Hortator 0.28.0 or later" with the installer link. Only INFO frames reached it.
5. INFO answered with another magic, or rc ≠ 0: "Not a Hortator editor device".
6. INFO `major` > 1: **a newer Hortator** — "use the editor from its release" with the release link; `major` < 1:
   "Update this FM-1". The same major with any minor: connected; `caps` decides what is shown.
7. Connected: WATCH 1, PAGES, DUMP; the state block from INFO. USB only: Bluetooth is not an editor link.

`proto.mjs` `classifyPort(name)` and `checkInfo(info)` implement 2–6.

## Appendix: the user sample slot

The slot layout (upstream Felucca's, kept: `firmware/src/eng_sample.c` reads it; `tools/sampleio.py` and the page's
`web/editor/sample.mjs` write it). Header at the slot's start, IMA ADPCM data at +512.

| Offset | Field |
| --- | --- |
| 0 | magic `"FSMP"` (u32 0x504D5346), u16 version 1, u8 zone count 1..16, u8 0 |
| 8 | name, 8 ASCII bytes (0-padded) |
| 16 | u32 data length (bytes), u32 CRC-32 (zlib) of the data, 8 bytes 0 |
| 32 | 16 zones × 28 bytes: u32 off (in the data), n (samples), loop start, loop end, rate (Hz / 44100 × 65536); i16 root × 16 (MIDI note), ADPCM predictor at the loop start; u8 step index at the loop start, lo note, hi note, looped (0/1). Unused zones: 0 |
| 480 | 32 bytes: not part of the header (0xFF in flash; a backup file holds them as read) |
| 512 | the data |

Data is IMA ADPCM, 4 bit, low nibble first, each zone starting from predictor 0 and step index 0; the decoder is
`eng_sample.c` `sample_next` (step table IMA_STEP, index table −1 −1 −1 −1 2 4 6 8; diff = step >> 3, + step for bit
2, + step >> 1 for bit 1, + step >> 2 for bit 0, negated for bit 3; predictor clamped to ±32767/−32768, index to
0..88). All little endian.

**The update loader's sweep.** After an update the loader (`firmware/loader/ldr_core.c`, frozen) reads 80 bytes at
+0xF00 of every 4 KiB sector in 0x93000..0xFBFFF — the sample slots included — and erases the sector when they read
as an update record: u16 at +6 = 0x5441 and u16 at +0 ≠ 0 and = CRC-16 (poly 0x1021, init 0, MSB first) of bytes
+2..+79. The chip's boot ROM looks for update records at the same place ("4 KiB boundary − 256"). Sample data fills
whole sectors, so a sample could, by chance (about 1 in 2^32 per sector) or by design, plant one. The device refuses
(SMP_DATA rc 2 detail 35) any piece whose window +0xF00..+0xF4F (bytes past the data's end: 0xFF, as flash holds
them) has u16 at +0 ≠ 0 and = that CRC-16 of +2..+79 — the CRC alone, a superset of the loader's test (about 1 in
65,536 per sector by chance) — and the page, before sending, finds such a window in its encoded data and moves the
sample by one source sample (drops the first) and encodes again until none is left. A slot's header sector
+0xF00 is data too. Bytes the device keeps erased (0xFF) never match (u16 0xFFFF ≠ 0xB613, the CRC-16 of 78 bytes 0xFF).
