# Machinedrum-style screen UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Redraw every screen of the Hortator firmware (FM-1, 240×240 RGB565) in the Elektron Machinedrum LCD style:
two-tone themes, the MD 3×5 pixel font at 2×, knob rings, dotted rules, inverted bars, shadowed popups, dither.

**Architecture:** A new 1-bit drawing layer (`md_*` functions, MD fonts generated from an ASCII-art source, a
two-colour theme) is added next to today's (Terminus fonts, 5-step palettes). Screens move to it group by group,
each task leaving the build and the host tests green; the last code task deletes the old layer. Layout constants
change once (Task 4), so every later task draws into the final geometry.

**Tech Stack:** C (single translation unit: the firmware `#include`s its `.c` files; tests include them through
`tests/ui_host.h`), Python 3 generators in `tools/` (run by `tools/build.py`, `--gen-only` for host tests), host
tests built and run by `tests/run_drum_tests.sh`.

**Spec:** `docs/superpowers/specs/2026-10-19-md-ui-design.md` (+ `docs/superpowers/specs/2026-10-19-md-ui/`:
mockup PNGs and `md.js`, whose `F`, `BIG`, `ICON` tables are the reference glyphs and whose `make()` helpers are the
reference geometry for every primitive).

## Global Constraints

- Two colours per theme, BG and INK; no third tone, no anti-aliasing anywhere. Dither = INK where
  `(x + y) % 2 == 0` in **screen** coordinates.
- Themes, in this order (index = stored id): MD RED `#e0472b`/`#38100a` (default), RED ON BLACK `#170605`/`#f0532f`,
  WHITE ON BLUE `#2445c8`/`#eaf1ff`, BLACK ON GREEN `#a3bf3c`/`#1c2a08`.
- Fonts: F3 = MD 3×5 caps drawn at integer scales (2× is the default: 6×10, advance 8, 1-px-wide glyphs advance 4);
  BIG = MD tempo digits 5×8 (2 px strokes, `1` is 3 wide). Lowercase draws as caps; a missing glyph draws as `?`.
- Lines, dotted rules, rings and outlines are 1 px.
- Layout A (screen y): top bar 0..15, knob row 17..59 (cells 60 px, dotted dividers x 60/120/180), solid rule 60,
  graph 61..180, dotted rule 181, trig strip 186..203, breadcrumb 212..238, 1 px INK frame round the screen.
- Nothing a user can see or do today is lost (the spec's §8 table says where each item goes).
- No audio-side cost; keep today's dirty signatures (`head_sig`, `ui.col[]`, `graph_signature`). No new large
  buffers.
- No Elektron files, bitmaps or screenshots in the repo. New files carry
  `/* SPDX-License-Identifier: GPL-3.0-only */` and `Copyright (C) 2026 DEADACTIVE`.
- After each task that changes firmware: `sh tests/run_drum_tests.sh` passes. After the last task: `./build.sh`
  (package + `build/site`) and `sh tools/build_sim.sh`.

## Review Focus

1. **A theme switch at runtime** (MENU > COLOR) must repaint every region; a cached signature that ignores the theme
   leaves stale-coloured strips → Task 3 adds the theme to the signatures and tests a full repaint.
2. **Dither seams between strips**: dither drawn in a strip canvas with canvas-relative parity shows a one-row
   phase break at strip boundaries → Task 2 tests the parity against screen y.
3. **Long / unknown strings** (project names with Latin-1, 5-letter labels, values like `16.0kHz`, `-24.0dB`) must
   fit their boxes without overrunning neighbours → Task 5 tests a 4-char value fit and Task 1 tests `?` for
   unknown glyphs.
4. **Old settings records** (palette 0..4, the BLE AUTOSTART bit 8) must load into a sensible theme without losing
   bit 8 → Task 3 tests every old id and bit 8.
5. **Touched-value timing**: the inverted value and the breadcrumb's full value must clear when `hot_t` runs out,
   and not stick on page changes → Task 5 tests both.

**Interfaces:**
- Produces:
  - `typedef struct { uint8_t h, first, last; const uint8_t *w; const uint8_t *rows; } md_font_t;` (`w[i]` = glyph
    width in px, 1..5; `rows[i * h + r]` = row bits, bit (w-1-c) = column c)

    glyph: Task 4 draws it with `cv_frame` + `cv_rect` (14×8 outline, 2×4 nub, three 3×4 cells).

### Task 2: MD primitives

**Files:**
- Modify: `firmware/src/gfx.c`
- Test: `tests/gfx_test.c`

**Interfaces:**
- Consumes: `md_text`, `md_text_w`, `MD_F3` (Task 1).
- Produces (all draw into the current canvas; `ink`/`bg` are RGB565):
  - `static int32_t cv_sy;` screen y of canvas row 0, set by `static void cv_begin_at(uint32_t w, uint32_t h, uint32_t sy, uint16_t bg)` (= `cv_begin` + `cv_sy = sy`; `cv_begin` keeps working with `cv_sy = 0`)
  - `cv_frame(x, y, w, h, ink)`, `cv_hdot(x0, x1, y, ink)`, `cv_vdot(x, y0, y1, ink)` (1-on/1-off starting at the
    first coordinate), `cv_dither(x, y, w, h, ink)` (INK where `(x + y + cv_sy) % 2 == 0`)
  - `cv_ring(cx, cy, r, ink)`: midpoint circle
  - `cv_knob(cx, cy, r, v1000, lfo1000, ink)`: `v1000`/`lfo1000` 0..1000 (`lfo1000 < 0` = none); geometry as
    `md.js` `knob()`: ring, tick 1 px at `cy - r - 2`, end stops 2×1 at radius r+2 at 225° and −45°, value blob 3×3
    centred at radius r−3.5 on the 270° sweep (225° → −45°), LFO hollow 3×3 at radius r+3; integer maths (a 64-entry
    sin/cos table or fixed-point; no float on the device)
  - `cv_tab(x, y, s, ink, bg)` → returns its width (INK box 13 px tall, `s` in F3 2× at x+3, y+2 in `bg`)
  - `cv_popup(x, y, w, h, title, ink, bg)`: BG fill, 1 px top/left, 2 px right/bottom (to y+h, x+w), notches at
    (x,y), (x+w-1,y), (x,y+h); title tab centred on the top edge from y−6, 15 px tall, padding 6
  - `cv_keycap(x, y, key, act, ink)` → returns the end x (1 px box 14 px tall round `key`, `act` 4 px after it)
  - `cv_button(x, y, w, s, on, ink, bg)`: 15 px tall; outline + INK text (off), INK box + BG text (on)
  - `cv_trigs(x0, y, on16, step, ink)`: `on16` bit i = trig i; box i at `x0 + i*14 + (i/4)*2`, 10×10 solid/outline;
    playhead (`step` 0..15, else none) = outline 14×14 at box −2; beat dot 2×2 at (box+4, y+14) for i % 4 == 0
